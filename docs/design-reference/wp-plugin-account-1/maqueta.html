4 · Cómo se hace

  1. La misma puerta que el conector de Claude. OAuth 2.1 con PKCE contra el servidor OAuth de Supabase que ya está encendido. Cada WordPress se registra solo (registro dinámico) con el nombre «GenScore para WordPress (dominio)» y su propia dirección de vuelta en wp-admin. Sin claves que copiar y pegar.
  2. Un cambio pequeño en GenScore. /api/ext/project acepta, además de la cookie de la extensión, un Authorization: Bearer, validado como ya hace el MCP (accountFromBearer + RLS del propio usuario, nunca service role). Las cifras son las mismas que ven la extensión, el MCP y la consola. Sin migración.
  3. El plugin guarda el token en la base de datos de WordPress, sin autocarga, y lo renueva él solo. Solo lo lee el servidor de WordPress; el navegador nunca lo ve. Las cifras se guardan 10 minutos como caché temporal para no llamar a GenScore en cada carga del escritorio.
  4. Desconectar desde el plugin borra el token; retirarlo en Ajustes > Apps conectadas de GenScore lo invalida desde nuestro lado.
  5. Sin ventas dentro de WordPress: ni precios ni pago, solo enlaces informativos, como en el MCP. Solo admins (manage_options) conectan y ven las cifras.
  6. WordPress.org: el readme declara el servicio externo (genscore.es y la autenticación de Supabase), con enlaces a términos y privacidad. Nada se llama sin que la persona pulse «Conectar».

Lo que hay que saber

  • Quien tenga acceso a la base de datos de esa web puede leer las cifras de la cuenta conectada mientras el token siga vivo. Es el mismo modelo que cualquier plugin conectado a un servicio; se mitiga con tokens cortos que se renuevan y el botón de retirar en GenScore.
  • El token de Supabase lleva los permisos de la propia cuenta (RLS), igual que el del conector MCP; el plugin solo lo usa para leer.
  • Toca autenticación, así que va en su propio PR con revisión de data-guardian y prueba en mi WordPress local con Plugin Check, y en tu web de Wasmer con tu cuenta.
